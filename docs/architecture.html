Technische Dokumentation

Architektur, die den Datenfluss sichtbar macht.

stickyflow.js übersetzt SFL-Quelltext deterministisch in eine Render-Szene und anschließend in SVG. Browser-Funktionen bauen als getrennte Schichten darauf auf; der statische Kern bleibt DOM-frei.

Framework-unabhängig Headless Core Explizite Layer Deterministisches SVG Architekturtests

Ziel und Leitlinien

Die Architektur trennt Sprachverarbeitung, semantische Auflösung, Render-Eingabe, Szenenaufbau, SVG-Serialisierung und Browser-Interaktion. Jeder Bereich besitzt einen fachlichen Grund zu existieren.

01

Eine Richtung

Niedrige Schichten kennen keine höheren Adapter, Renderer oder Browser-Runtimes.

02

Fachliche Module

Ordner und Funktionen benennen konkrete Domänen. Catch-all-Strukturen sind verboten.

03

Kleine Orchestratoren

Orchestratoren wählen, sequenzieren und montieren. Berechnung bleibt in spezialisierten Modulen.

04

Stabile Verträge

Öffentliche Imports und DOM-Attribute bleiben bei internen Refactorings kompatibel.

05

Pure zuerst

Parser, Geometrie, Scene-Aufbau und SFL-Patches sind von DOM und globalem Zustand getrennt.

06

Getestete Grenzen

Importregeln, Browser-Tiers, Entry-Points und verbotene Ordner werden automatisiert geprüft.

Datenfluss

Jede Stufe übernimmt genau einen Übergang. Zwischenrepräsentationen verhindern, dass Parserdetails in SVG-Code oder Browserzustand durchsickern.

Der direkte Standardpfad lautet render(SFL) → RenderResult. Hosts mit bereits aufgebautem RenderInput verwenden renderCanvas(input) und überspringen die SFL-Stufen.

Wo entsteht das Modell?

Es gibt nicht „das eine Modell“. Vier bewusst verschiedene Repräsentationen beantworten vier verschiedene Fragen. Eine neue SFL-Eigenschaft durchläuft diese Verträge nacheinander.

R1

SflDocument

Syntaxmodell: Welche Blöcke, Properties und Werte stehen im Quelltext?

  • Definiert in sflLanguage/ast.ts.
  • Erzeugt von parse().
  • Bewahrt Sprachstruktur, nicht Rendersemantik.
R2

SflCanvasState

Semantikmodell: Was bedeuten Definitionen, Vererbung, Gruppen, Positionen und Links?

  • Definiert in sflSemantic/types.ts.
  • Erzeugt von sflToCanvasState().
  • Enthält SflEntityOut und Diagnosen.
R3

RenderInput

Renderer-Modell: Welche konkreten Shapes, Frames, Tabellen, Charts und Links sollen gezeichnet werden?

  • Definiert in renderInput/types.ts.
  • Verwendet Typen aus model/.
  • Enthält keine SFL-AST-Knoten.
R4

RenderScene

Zeichenmodell: Welche Rects, Paths, Ellipsen, Bilder und Texte werden in welcher Reihenfolge ausgegeben?

  • Definiert in rendering/scene/types.ts.
  • Erzeugt von buildRenderScene().
  • Ist unabhängig von SFL und vom DOM.
Die dauerhaften fachlichen Definitionen beginnen in model/, beispielsweise model/shape/types.ts → Shape. Der Parser erzeugt diese Typen nicht direkt. Erst der Adapter renderInput/fromSfl übersetzt den semantischen SFL-Zustand in diese Model-Objekte.

Ein Shape von SFL bis SVG

Dieses Beispiel verfolgt eine einzelne Entity durch jede relevante Funktion. Die Zwischendarstellungen sind gekürzt, zeigen aber die tatsächlichen Verträge und Zuständigkeitswechsel. 

sfl 1.2

Model Demo {
  Entity start {
    shape: rounded_rectangle
    text: "Start"
    layout {
      position: 40, 60
      size: 160, 80
    }
    style {
      fill: "#0f766e"
      stroke: "#5eead4"
      strokeWidth: 2
    }
  }
}
01

Öffentliche Orchestrierung

render(source) delegiert an sflToRenderInput(source) und danach an renderCanvas(input). Die Funktion kennt keine Parser- oder Shape-Details.

src/render.ts → render() / renderCanvas()
02

Tokenisierung

tokenize() liest Zeichen über SourceCursor. readNextToken() delegiert an spezialisierte Leser für Identifier, Zahlen, Strings, Zeilenumbrüche und Satzzeichen.

sfl/lexer.ts → language/lexing/tokenizer.ts → nextToken.ts
03

AST-Aufbau

DocumentParser.parseDocument() prüft Header und Version. BlockParser erzeugt anschließend verschachtelte SflBlock- und SflEntry-Objekte.

{
  version: "1.2",
  blocks: [{ kind: "Model", name: "Demo", entries: [/* Entity start */] }]
}
sflLanguage/parsing/parser.ts → document.ts → blocks.ts → properties.ts → values.ts
04

Semantische Auflösung

createCanvasResolution() indexiert Definitionen und baut die Property-Auflösung. CanvasTreeReader traversiert das Model. buildEntity() vereinigt Klassifikation, Geometrie und Präsentation.

{
  id: "start", entityType: "shape", shapeType: "rounded_rectangle",
  text: "Start", x: 40, y: 60, width: 160, height: 80,
  props: { fill: "#0f766e", stroke: "#5eead4", strokeWidth: 2 }
}
sflSemantic/sflToCanvasState.ts → canvasState/resolution.ts → canvasTree/resolver.ts → canvasObjects/processing/resolver.ts
05

Übersetzung in das Domain Model

collectEntities() trennt die Entity-Varianten. Für diesen Eintrag ruft es shapeObject() auf. Dort werden SFL-Werte validiert, Farben dekodiert und in den stabilen Shape-Vertrag übersetzt.

{
  id: "start", type: "shape", shapeType: "rounded_rectangle",
  text: "Start", x: 40, y: 60, width: 160, height: 80,
  fillColor: "#0f766e", strokeColor: "#5eead4", strokeWidth: 2
}
sflToRenderInput.ts → renderInput/fromSfl/entities/collect.ts → shape.ts
06

Scene-Aufbau

buildRenderScene() wählt den Shape-Workflow. buildShape() erstellt Kontext und Style. renderShapeGeometry() wählt über GEOMETRY_RENDERERS den Rectangle-Renderer; Text wird separat erzeugt.

[
  { type: "rect", id: "shape-start", x: 40, y: 60, width: 160, height: 80, rx: 8, ... },
  { type: "text", id: "shape-text-start", lines: ["Start"], ... }
]
rendering/scene/build.ts → entities/shape.ts → shape/geometry/index.ts → simple.ts
07

Identität, Reihenfolge und Bounds

tag() ergänzt SceneIdentity mit Rolle, ID, Kind und Primary-Flag. Danach sortiert der Scene-Builder stabil nach order und ID und berechnet die Gesamtgrenzen.

rendering/scene/tagging.ts → scene/build.ts → scene/bounds.ts
08

SVG-Serialisierung

renderSvgDocument() erzeugt ViewBox und Definition-Registry. nodeSvg() dispatcht anhand von node.type. Attribute, Styles und DOM-Contract werden in getrennten Modulen serialisiert.

<rect id="..." data-sf-role="entity" data-sf-id="start"
  data-sf-kind="rounded_rectangle" data-sf-primary="true"
  x="40" y="60" width="160" height="80" rx="8" .../>
rendering/svg/renderScene.ts → document.ts → nodes.ts → attributes.ts / contract.ts
09

Optionale Browser-Nutzung

Der Viewer setzt das fertige SVG in den Container und prüft den DOM-Contract. Interaction kann anschließend Auswahl und Editing binden, ohne Parser oder Renderer umzubauen.

viewer/display → viewer/interaction → interaction/*
Für die vollständige Datei-für-Datei-Ansicht dieses Beispiels siehe Rounded Rectangle: vollständiger Execution Trace.

Ordnerstruktur

Der Top-Level zeigt technische Schichten; innerhalb des Renderings erfolgt die Navigation nach Domäne.

├─ sflSemantic/            Definitionen, Vererbung, Canvas-Object- und Link-Auflösung
├─ importJson/             Export in das Stickyflow-Importformat
├─ renderInput/
│  ├─ fromSfl/             SFL-Zustand → RenderInput

│  ├─ scene/              Scene-Vertrag, Aufbau, Bounds, Paint, Reihenfolge

Layer im Detail

Die Karten beschreiben Besitz, Ein- und Ausgabe sowie die Grenze jeder Schicht.

L0

Model

Framework-neutrale Diagrammtypen, Farben, Geometriealgorithmen und grundlegende Verträge.

  • Kennt keine SFL-Syntax.
  • Kennt weder Scene noch DOM.
  • Besitzt Point, Bounds und Diagnosen.
src/model
L1

SFL Language

Lexikalische und syntaktische Verarbeitung der Sprache sowie kanonische Ausgabe.

  • Text → Tokens → AST.
  • AST → kanonischer SFL-Text.
  • Keine Diagrammauflösung.
src/sflLanguage
L2

SFL Semantic

Löst Definitionen, Kompositionen, Vererbung, Gruppen, Entities und Links fachlich auf.

  • AST → SflCanvasState.
  • Sammelt SFL-Diagnosen.
  • Keine Render-Nodes.
src/sflSemantic
L3

RenderInput

Stabiler Eingabevertrag des Renderers und Adapter vom semantischen SFL-Zustand.

  • Positionierte Model-Objekte.
  • Aufgelöste Link-Endpunkte.
  • Keine Scene- oder SVG-Abhängigkeit.
src/renderInput
L4

Render Scene

Baut aus RenderInput eine deterministische, geordnete Liste abstrakter Zeichenknoten.

  • Berechnet Bounds und Paint.
  • Taggt fachliche Besitzer.
  • Berührt kein DOM.
src/rendering/scene
L5

SVG

Serialisiert Scene-Nodes, Paints, Marker, Filter und den DOM-Vertrag in ein SVG-Dokument.

  • Escaped nutzergesteuerte Werte.
  • Erzeugt Definitionen deterministisch.
  • Gibt String, Größe und Diagnosen zurück.
src/rendering/svg

Browser-Layer

Browserfähigkeiten werden opt-in auf den statischen Kern gesetzt. Die Richtung ist streng einseitig.

ViewerSVG-Mount, Camera, Selection, Display-Patches
→
InteractionMove, Resize, Text, Link-Endpunkte, SFL-Patches
→
Web ComponentBrowser-API und deklaratives Custom Element
Die Pfeile zeigen die erlaubte Nutzung des jeweils niedrigeren Layers. Der Core importiert niemals Viewer, Interaction oder Web Component. Interaction erreicht Viewer nur über dessen öffentlichen Einstieg.

Qualitätssicherung

Die Architektur wird nicht nur beschrieben. CI prüft Struktur, Verhalten, Typen und das gebaute Paket.

Biome prüft Formatierung, Lint-Regeln und Assists.
TypeScript läuft ohne Ausgabe und mit strikten Dead-Code-Regeln.
Core-Allowlist verhindert rückwärts gerichtete Imports.
Runtime-Boundaries halten den statischen Kern DOM-frei.
Package-Tests sichern alle vier Entry-Points und Formate.
Golden-SVGs sichern deterministische Ausgabe.
DOM-Tests prüfen Viewer- und Component-Lifecycle.
Build plus Smoke-Test validieren das veröffentlichte ESM-Paket.
Maßgeblicher Gesamtcheck: npm run ci. Zusätzlich wird git diff --check separat ausgeführt. Strukturtests liegen unter test/architecture.
